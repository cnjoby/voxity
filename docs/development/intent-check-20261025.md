# 三种自然语言意图实测

时间：2026-10-25 10:06–10:11，Asia/Shanghai。代码基线：`d7411ea`；本轮未修改业务源码、平台提示词或部署。测试期间已有未跟踪的 `docs/planning/`，未改动。

## 结论与假设

“闲聊”按与声呐 AI 私人聊天理解；如果指找附近真人闲聊，本轮没有验证该能力。第二句按用户尚未到达目的地、希望了解目的地或前往路线的当前拥堵理解。第三句没有给出景区名称，也没有提供可确定景区的导航上下文。

| 原话 | 私人语音入口实测 | 现场交流接口实测 | 当前能否满足 |
| --- | --- | --- | --- |
| Hi，声呐，我想闲聊 | 正确识别，回复“你好呀，想聊点什么？” | `ignored / ignore`，未公开 | AI 私聊单轮可用；没有验证持续聊天或真人匹配 |
| HI，声呐，我想去张江人工智能岛，现在堵车吗 | 识别目的地和路况询问；答复没有实时路况、没有相关现场候选 | 人在授权目标附近时能发布 `question`；不在目标附近时返回 `409 PRESENCE_REQUIRED` | 尚不能从这一句话完成远程询问及返回实时答案；路线与出发地也没有解析 |
| HI，声呐，前面景区还有停车位吗？ | 识别成功，答复没有相关候选，并追问“你问的是哪个景区？” | 地点不明确仍判为 `question`，并发布到会话预选地点“张江人工智能岛” | 当前不能可靠满足；私人入口有澄清，自动发布通道存在目标误投问题 |

三个输入均收到真实 STT、完整 TTS 结束事件和音频字节。它们证明合成输入可经过真实云端协议往返，不代表真人唤醒、手机扬声器听感或车内设备通过验收。

## 真实云端语音证据

使用 macOS Tingting 合成用户原话，转换为 16 kHz / PCM16 / 单声道，借助已授权的既有设备绑定，通过独立协议客户端执行 OTA/WSS。没有操作实体手机、安装 APK、启用麦克风或播放返回音频。每句独立连接，未测多轮记忆。

| 输入 | STT | 回复摘录 | 从该句测试开始到 TTS 完整接收 |
| --- | --- | --- | --- |
| 闲聊 | 嗨，声呐，我想闲聊。 | 你好呀，想聊点什么？ | 7.74 秒 |
| 路况 | 我想去张江人工智能岛，现在堵车吗？ | 我这边没有张江人工智能岛的实时路况信息……建议你直接打开地图导航看一下实时路况…… | 42.67 秒 |
| 车位 | 嗨，声呐，前面景区还有停车位吗？ | 目前我这边没有景区停车位的相关候选信息……你问的是哪个景区？ | 25.20 秒 |

时间包含连接、按实时节奏上传及整段 TTS 接收，不能解读为首字延迟。样本少，不能据此判断成功率或稳定延迟。

路况回复还提及旧个人关注和已过期回答，并追加天气等无关提议；车位回复先播报“让我先获取一下当前的配置和候选信息”。回复偏长，且工具操作播报不符合现有提示词要求。候选是否为空在这里属于助手的答复，未用业务日志独立证明其每次实际工具调用。

## 判定与隔离 HTTP 证据

直接调用真实 Bamboo `ExchangeDecider`，使用现行判定策略，显式设置授权地点“张江人工智能岛”，关注为空、无已听上下文、无邀请：三句分别得到 `ignore / question / question`。

随后使用现有 ASGI 应用、临时 SQLite 库、合成静音 WAV 与原句文字、注入的测试定位，执行创建会话和提交发言。判定仍调用真实 Bamboo，没有替换为决策桩。各独立问题验证后在临时库取消，再执行下一句：

- 闲聊：HTTP 200，`status=ignored, action=ignore`，未生成公开帖子。
- 路况：HTTP 200，`status=published, action=question`，持久化目标 `test-ai-island`。
- 车位：HTTP 200，`status=published, action=question`，持久化目标同样为 `test-ai-island`；没有确定“前面景区”的实际对象。
- 将同一测试用户的位置移到远离目标的注入坐标，再提交第二句：HTTP 409，`PRESENCE_REQUIRED`。该自动交流接口先校验人在目标附近，尚不能承担行前远程提问。

首轮 HTTP 探测在第二句后保留了等待中的问题，使第三句被 `QUESTION_ACTIVE` 暂缓；最终结果来自消除该用例相互影响后的复跑。语音脚本在三句完成后曾因模块导入路径中断，修正后只补跑判定阶段，没有重复算作另一轮语音验收。

## 能力断点与建议验收条件

当前公网 `/healthz` 为 200，实时读取的 OpenAPI 含自然交流接口；公网 MCP `tools/list` 实际只返回 `probe / get_feed / set_focus / queue_voice`。本轮未独立核验服务器运行文件的 revision，不能把历史部署记录当作本次来源证明。

1. **语音助手与业务执行没有贯通。** 私人助手 MCP 没有发布问题工具；Android 现场服务使用 STT 后另走 Sonar HTTP，也不会把 `ignore` 发言转交私人助手继续对话。因此，同一句话在两个入口得到的行为不同。
2. **目的地与当前位置尚未形成独立的自然语言执行路径。** 自动发布要求本人在会话目标附近（`server/app/exchange.py:325`），新问题的目标直接取会话地点（`:401`）。旧 App 手动草稿可以手选远处目标，但不能算上述一句话已自动完成。
3. **“前面景区”没有可靠消歧。** 需要已确认的行程/目的地，或一次简短澄清后才建立目标。不能以已有会话地点代替用户实际所指对象。本轮复现了误投；尚未评估发生率。
4. **实时答案缺少数据和收听接入。** 现有高德适配做定位、地点解析与 POI 搜索，没有路况或剩余车位查询。停车场运营公告虽有独立业务实现，`get_feed` 当前只选 `question / answer`（`server/app/service.py:901`），没有将公告、现场 scene 接入这个私人语音查询入口。

下一轮验收应分别覆盖：私人闲聊不公开；明确目的地的远程问人任务可以建立并追踪；缺失景区时只澄清、不得误投；实时答案携带来源和时间，无有效信息或无人回应时明确告知。若采用真人原声路线，应验证真实提问—现场参与者—回复回传；若采用地图/运营数据路线，应单独验证对应数据接入，不能以模型生成内容替代。
