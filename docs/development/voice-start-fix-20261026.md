# 0.3.0 语音启动与真机 Opus 上传故障

日期：2026-10-26，Asia/Shanghai。范围为 Android 手机链路；ESP32 配置和固件独立维护。

## 现场与根因

手机 vivo V2405A/Android 16 已安装 0.3.0/code11。现场截图显示“私人语音平台的工具配置尚未核验”，此前日志连续进入 `unavailable`。线上进程工作目录为 `20261026-opus-contract-031`，发布清单匹配，健康检查 200；Alice/Bob 的 `client_managed_voice` 均为 false，核验名单为空。

第一处故障：Android 启动强制声明 `client_managed_voice=true`，服务端按现有门禁返回 `503 / VOICE_PLATFORM_NOT_VERIFIED`。手机 Agent 仍绑定默认音乐、新闻、天气插件及 Sonar MCP；尚未满足预生成语音的工具执行隔离前提。

解除启动门禁后，真实手机进入 `ready`，完成 Linx WSS 握手和 STT，业务上传后进入 `unknown`。对原请求只读核对返回 `404 / REQUEST_NOT_FOUND`，未自动补发。

第二处故障：在同一台手机上以合成正弦波复现，原生编解码检查通过，但服务端 PyAV 校验拒绝。5 秒文件声明 240,000 个 48kHz 样本，实际解码 240,648 个；2.48 秒文件声明 119,040 个，实际解码 119,688 个。真机编码器比此前模拟器多输出一个尾部填充包，原有修正只改最后一页 granule，造成 EOS granule 小于前一页，违反正确的结束裁剪时间线。源音频并未超过时长或大小上限。

第三处故障：Opus 修复后已有多轮私人聊天和业务回应成功。连续说话时，在第一轮仍等待服务端时捕获的第二段被保留为私有并触发重试提示音；提示音先取得播放门禁，第一轮随后开始的流式回复抛出 `IllegalStateException`。22:53:09.993 的 `system_feedback_started` 早于 22:53:11.116 的首个回复音频，随后进入 `assistant_unavailable`。这是两个独立播放任务的争用。

## 修复

- 仅调整手机 Sonar Agent：`Intent_nointent`、`functions=[]`、MCP 绑定列表为空，使用[手机私人语音提示词](../design/linx-android-managed-voice-prompt.md)。回读确认 ASR、LLM、TTS、音色、记忆、设备绑定等保留；ESP32 Agent 配置逐字段相同。
- 平台核验后，仅将手机本人实际映射的 Agent 加入生产 `SONAR_MANAGED_VOICE_VERIFIED_AGENTS`。服务重启后 Alice 可用、Bob 仍未放行；保留未核验身份的门禁。
- Android 0.3.1/code12：Opus 文件在第一个覆盖原始样本和 pre-skip 的完整包结束，删除多余填充包/页；如在页内结束，重建 lacing、payload、EOS 和 CRC。保留服务端严格校验、原录音时长和幂等字节缓存，不增加 WAV 回退分支。
- Android 的业务错误日志记录 HTTP 状态和受限错误码，不记录语音正文或凭证。
- 非致命提示音等待已在进行的提交/流式回复结束才播放，实际起播时复查新轮次和收音状态；提示音结束同步清除界面播放状态。新增原生服务回归，模拟等待首个音频时出现重试提示，确保回复先完成且未被取消。

## 验证与设备验收

平台修复后已在用户手机确认进入“正在听”。初次真人测试暴露上述第二处故障，不能视为完整对话通过。

门禁相关后端回归 5 项通过；Android 61 项 JVM 测试通过、无跳过，Lint 和 Debug/测试 APK 构建通过。新增回归使用实际 vivo 编码的合成波形文件 `fixtures/vivo-opus-extra-padding.opus`，不含用户录音；另增加非整秒时长的原生设备检查。

0.3.1 APK：`output/sonar-0.3.1-voice-start-fix.apk`，最终构建 SHA-256 `e242fee655396542e16f4c1e3168d39c13178be66f616a4a88ec2c7f91feb03f`。本机报告、截图、平台回读、合成音频和手机私有配置备份在忽略目录 `output/voice-start-fix-20261026/`，私有内容不进入公开交付。

0.3.1 在同一台 vivo 上 6 项原生音频测试通过，5 秒和 2.48 秒合成样本分别经服务端严格校验，解码 WAV 为 160,044 和 79,404 字节，声明时长与实际样本一致。隔离 HTTP 环境的原生 Opus 上传/下载均为 200，下载字节保持一致，没有写入生产数据。覆盖安装前后的加密连接配置与灵矽身份文件逐字节相同。

最终 APK 已保留数据覆盖安装。手机整组检查已完成 6 项原生音频和 6 项服务控制，随后设备退出记录显示 `single-cleaner / FORCE STOP`，该轮整组不计全通过。后续单项手机自动检查未完成，也不计通过；测试期间的隔离连接已从安装前备份恢复。新增提示音冲突回归改在独立 API36 模拟器运行，**1 项通过**（7.882 秒）；模拟器已关闭。

23:09 后用户在最终 0.3.1 手机上重新测试，日志显示 Linx 识别、Opus 业务提交、私人流式播放和业务回应完成；另有真实提问成功发布。用户明确确认：**“回复和控制都正常”**。已查看最终手机“声呐正在回应 / 合成语音”截图；真人扬声器出声和安静/继续以用户确认作为验收证据。此次启动故障、Opus 上传和提示音争用修复完成，不代表车内 AEC、ESP32 或所有业务意图均已验收。

收尾时生产仍为031，健康 200、数据库完整性和外键检查通过。原159条消息均保留，运行期间用户正常测试后共162条；users、Token和设备映射与配置前相同，其他服务器环境值相同。手机灵矽身份文件仍与安装前逐字节相同；加密连接文件在后续使用中重新保存（`iv`/`sealed` 变化），不将最终文件表述为逐字节不变。

## 配置和数据保护

服务端未更换源码发布目录。配置与 SQLite 在线备份位于 `/var/backups/voxity/phone-voice-enable-20261026T144216Z/`；配置仅改变核验名单，其余环境值相同。159 条既有消息和 159 份原始音频全部保留、音频摘要一致，users 身份相同。`GET /v1/me` 会按既有远程地点固定规则刷新定位的时间戳，profiles 的 `updated_at`、`location_json`、`sampled_at` 因此变化；关注、模式、授权和修订号未因配置放行改变。

撤销时先移除手机核验名单并重启服务，结束受影响的托管语音会话，再恢复该 Agent 的原配置和 MCP 绑定。平台快照已保留在私有输出目录。不要用旧数据库覆盖运行期间新增记录。
