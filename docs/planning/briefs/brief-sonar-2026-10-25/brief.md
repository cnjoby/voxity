面向黑客松评委的内容草案。用户已确认目标与团队资源；商业选择和验证方案中的推断使用 `[ASSUMPTION]` 标记，尚无付费与规模化证据。

## 一句话与路演主线

**声呐以车内免提语音为入口，让车主听见现场的人，也让地点的有效信息找到需要它的人。**

延续“听见同路的声音”。产品是由人发声、声音广场（公共讨论空间）组织声音、个人 Agent 管理注意力与等待的城市声音社区，串联人、车、地点和事件，兼有现场问答与可留存的异步原声。

`[ASSUMPTION]` 首个商业起点建议是一处授权停车场或景区入口：先验证 POI 运营方是否愿意为发布管理与到访时的信息送达付费。

路演顺序：车主的现场信息缺口 → 真人问答演示 → AI 如何减少干扰 → 认证 POI 的商业试点 → 团队接入基础 → 下一步验证。

## 让人愿意听下去的三个时刻

以下是演示故事，尚未取得用户访谈证据：

- **到了景区，还没找到入口。**“哪个停车场还有位？导航带到的入口已经排满，另一边能不能进？”需要的是刚到过的人或停车场运营方的当前信息。
- **堵在事故后方，只能猜。**“前面是在缓行，还是临时封闭？刚经过的人能说一句吗？”需要带来源与时间的现场观察，帮助判断后续安排。
- **接人快迟到了，地图上的红线还不够。**“这个路口现在能不能过去？队伍开始动了吗？”需要一条与当前路段、方向有关的回答。

地图、群聊和人工问询各有价值；声呐要验证的缺口是：用户有具体问题时，能否找到此刻在场且愿意回应的人，并在无需持续盯屏的情况下等到答案。

## 核心价值与 AI 分工

对车主，价值是减少出行中的未知、寻找信息的操作和无关打扰。对回应者，参与可以短暂、自愿，也可以保持安静。对 POI 运营者，价值假设是一次发布有效告知，让适用的到访者及时获得，减少重复问询与错误入口排队。

先根据权限、地点、时效、用户授权与静音规则决定信息能否送达；快速决策模型从预设动作中选择；LLM 整理地点、事件和问题意图，辅助匹配。现场事实来自人或授权运营方，保留原声、来源与时间。

**审核与注意力判断分开：**内容审核拟判定通过、拦截或待复核；个人 Agent 决定是否提醒、稍后处理或忽略。当前文档记录已接入的是邀请提醒决策，完整内容审核尚待验证。内容通过审核不等于事实已核实；LLM 不补写未知现场答案。

## 从产品价值走向商业验证

`[ASSUMPTION]` 建议先用一个停车场或景区入口做封闭试点：认证运营方提供基础告知，小范围参与者提供现场补充与问答。先验证单点服务价值，再扩大地点与车主覆盖。

| 场景 | 在 BP 中承担的角色 | 商业假设 |
| --- | --- | --- |
| 停车／事故／拥堵互助 | 证明车主为什么需要声呐 | 需验证回应密度、等待时间和重复使用意愿 |
| 认证 POI 公告与问答 | 首个付费试点候选 | POI 运营方可能为发布管理、到访时的信息送达与服务效果付费 |
| 品牌服务 | 相邻扩展 | 用户主动提出需求后，连接可履约的服务方，探索服务费 |
| 拼车／用车撮合 | 长期扩展 | 另验供需密度、履约及合作模式，尚无交易证据 |

`[ASSUMPTION]` 优先测试 POI 订阅／试点服务费；主机厂集成费取决于另行确认的合作范围。品牌转化与撮合收入放到后续验证阶段。定价、续费、成本与分成均未验证。

## 为什么由我们开始，以及怎样证明

用户确认已有 xAtom 智能硬件、灵矽，以及主机厂对底座的合作意向；**声呐试点尚待明确**。这些构成语音入口开发与试点洽谈的基础，声呐的预装、可触达车主数和商业订单仍需另证。

项目文档记录：服务端与双用户模拟器的问答闭环、公网部署、手机真机上的灵矽私人助手语音交互，以及 POI 公告前台扩展已有进展；完整真人公开问答、ESP32 与车内体验待验收。核对方式见补充材料。

`[ASSUMPTION]` 首轮验证分两部分：双用户演示证明问答关联、原声回传与静音生效；一个授权 POI 试点验证公告有效性、实际听到率、重复问询变化和付费意愿。指标保留分母与失败记录，付费证据以报价反馈、付费试点和续用为准。

路演落点：**先证明“车到了，信息也到了”，再证明有人愿意持续使用、有人愿意为此付费。**
