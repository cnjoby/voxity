# 声呐 Sonar｜两天黑客松架构评审

日期：2026-10-23  
评审范围：产品理念、两天交付范围、Linx 接入、双端音频和单机服务。  
证据：本次检查的设计文档与 Linx 官方协议，尚无两端联调、部署或设备实测证据；ESP32 由另一位成员实现，其完成程度未纳入本次事实判断。

## 结论

**有条件适合。以“人发起问答，广场组织声音，个人 Agent 辅助收听和追踪”为分工，比赛围绕一个路口的真人互助组织第一条闭环。**

广场按权限、地点与时效提供声音候选，个人 Agent 按主人意愿决定是否提示、何时播放及是否继续等待。共用一台服务器和策略代码不影响个人状态独立；无需为每位用户部署独立模型进程。

关键路径在双端与 Linx 的联调，不在数据库规模。不能仅凭四张表、三个工具就判断实现量很小。两天适合做一个固定现场、两个真实参与者的互助演示，不宜承诺完整的城市语音社区。

## 主要发现

### P1：删除所有主动提示，会丢失“我能帮助谁”的核心价值

用户在中环路金科路口，另一个人发问时，其 Agent 应发现自己处在现场，询问是否愿意回应。仅在用户说“听听新消息”后筛选，无法完成这个体验。

建议：把“已授权现场互助模式下的询问提示”列为必做；延后泛化的闲聊推送、全天候后台 Agent 与智能体间自主协商。主动链路由本机业务事件和每个人的独立策略触发，提示由客户端播放，不依赖远程唤起 Linx。

### P1：原声与 Linx 转写关联仍是未验证的协议依赖

设计要求两端都把本轮音频送至 Linx，再把转写与原声配对上传。官方展示的 STT 消息含 session_id 与 text，不能据此推定有业务 turn_id 或最终转写标志。一个会话可能包含多轮；迟到识别结果会影响公开内容与回复归属。[设备协议](https://linx.qiniu.com/docs/xrobot/platform/websocket)

建议：手动短录音、每端只保留一个待处理轮次、明确完成与超时条件；将问题ID与录音轮次绑定。先验证“两端各一条真实录音→正确转写→正确回复关系”，再展开界面。缺少转写或关联不明时保留私人草稿，不发布。带人工转写的测试样本可用于先测个人策略，必须标明测试方式。

### P1：平台接入关口尚未闭合，不能视为即插即用

Linx 文档支持设备注册、语音协议与云端 MCP；这不等于现有 Android 工程已具备可运行客户端。MCP 身份 Header 也不等于调用方鉴权完成。两端同时从零开发音频、注册、工具调用与业务上传，会使比赛结果依赖多个未验证环节。

建议：先拿到实际设备语音往返、MCP 调用身份与凭证、外部原声播放三类证据。平台管理密钥留在服务器。若任一端接入未完成，应明确该端演示能力缺口，不以另一端成功替代它的验收。[OTA](https://linx.qiniu.com/docs/xrobot/platform/OTA)、[云端 MCP](https://linx.qiniu.com/docs/xrobot/mcp/software-mcp)

### P1：只展示“能问能播”，不足以证明个人 Agent

如果两人的地点与候选都不同，输出不同也可能只是地点过滤；如果只展示一位用户切换频道，评委难以判断个人目标是否起作用。

建议：演示同一地点、同一个问题下，两种明确意愿：“愿意回答附近路况”与“现在安静”。前者得到询问提示，后者不被打扰。恢复参与后，用一条新问题验证再次生效。展示目标、现场上下文、处理结果及一句依据，不展示模型内部思维过程，不伪造过滤理由。

### P2：播放与取消缺少跨通道的任务边界

只在入队时校验配置版本不足以防止旧结果播放：用户修改关注、停止或离开现场后，已入队结果及迟到工具调用仍可能到达。只等待 TTS stop 也不能处理“根本没开始 TTS”或连接中断。

建议：每次询问、回答邀请和播放都带 request_id；收听任务带 revision。过期、拒绝和取消使对应邀请失效，模式改变时重新检查待提示和待播内容；静音不自动结束自己的提问任务。取队列和实际播放前再次校验。客户端单路播放，并为 TTS 未开始、已中断、缓冲未排空定义状态；停止或失败时取消本次播放，避免无限等待或自动反复播放。

### P2：开发顺序应把核心机制提前

先把第一天花在两端完整原声功能，第二天再接个人化，容易最终只交付语音收发。

建议：先用明确标注的预置声音跑通“问题→个人策略→提醒→原声回答”，再替换成现场录音。第一天结束应已出现一次个人选择及真实设备提醒；第二天优先完成实时收发、拒绝与不打扰、联调和路演，新增场景排在后面。

## 什么必须保留

| 必须证明 | 最小实现 |
| --- | --- |
| 人是问答主体 | 问题与答案均由人提出并确认，Agent 负责协助与追踪 |
| 广场组织真人声音 | 一条现场问题、一条真人原声回复，显式关联并补全时间、地点与来源 |
| 每个人有自己的意愿 | 本人配置参与互助或保持安静，服务端分别执行个人策略 |
| Agent 能发现我能帮谁 | 发问者无需指定回答者；现场用户收到一次询问提示 |
| 主人保有决定权 | 可以回答、拒绝或不回应；Agent 不替人编造或自动公开回复 |
| 信息有来源 | 播放原声，标明是谁、何时、模拟或实际现场信息 |

保留单机 FastAPI、SQLite、文件目录，以及独立 Agent 与用户映射。为比赛做一段请求范围内的主动任务即可；不要求长期自主循环。

## 两天范围建议

- **必做**：一个预设路口、两位用户、一次公开提问、一次个人策略判断、一次主动提示、一次原声回答、一次静音反例。
- **完成核心后再做**：同路闲聊筛选、同景区目的地筛选、更多消息展示、连续追问。
- **延后**：真实道路定位、长期记忆、离线系统通知、开放语音房、自动多轮找人、多端账号同步。

问题语音及用户位置可预置用于早期联调，但最终演示至少包含一次现场发问和一次现场真人回答。主动提示可使用预录的系统提示音；这是固定交互素材，不是伪装的真人或伪造的模型输出。

## 推荐主演示

1. A 在前方路口之外问：“现在中环路金科路口堵不堵？”
2. B 的场景配置为“在路口，愿意回答附近路况”，其个人策略接住该请求。
3. B 的设备响提示音：“有人询问中环路金科路口堵不堵，愿意回应吗？”
4. B 自愿录制：“好堵啊，下匝道都要十五分钟。”确认公开后，A 听到 B 的原声和时间来源。
5. B 切换为“现在安静”，A 发出新问题，B 不再收到提示；A 得到无人回应或暂不可用的真实状态。

“十五分钟”保留为回答者的现场说法，不自动转成全路段通行预测。地点与方向用演示配置，不宣称已做 GPS 路况识别。

## 通过条件

- 两端、Linx 与 MCP 的实际接入均验证；不能只凭接口文档确认完成。
- 现场请求能跨两个用户走完一轮，至少连续三轮无串错回复。
- 同地点下个人意愿能改变提醒结果；旧问题过期、已答或被拒绝后不反复提醒。
- 画面能看到请求、个人配置、邀请结果和原声回复，评委无需读代码才能理解机制。
- 单机重启后内容仍存在；断连时不宣称任务仍在正常执行。

上述边界与建议已纳入[项目架构](architecture.md)，仍需实际开发和接入验证。当前结论为设计层面的有条件可行，不是两天完成的保证，也不是已通过设备验收。
