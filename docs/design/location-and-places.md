# 声呐｜真实位置与地点关联设计

日期：2026-10-24。状态：Android 前台定位、真实高德 POI 与附近问答已实现，实体设备待验收。实现接口与测试入口见[定位接入](../development/location.md)，旧模拟 v1 协议兼容保留；道路方向和拓扑仍未实现。

## 用户交互

首页的工作是说一句、确认发出、等待并听回复。定位与地点解析在后台完成，不让用户先配置坐标、方向、GIS 或 Agent。

首次使用相关功能时申请前台定位权限。页面显示实际解析到的地点及“当前位置”；定位失败、仅有粗略位置或拒绝权限时，允许手选提问地点，明确显示“手选地点”。手选提问地点不能证明用户身处该地，不生成“你恰好在现场”的回答邀请。当前模拟版本始终显示“演示地点”，不冒充真实定位。

没有指明地点的问题默认问当前位置附近；明确说出“中环路金科路口”时，解析为提问目标，即使本人还在远处。公开前显示一句“问：中环路金科路口”，可点选修改。重名、无法确定的地点只给少量选项，不擅自替用户选定。首版地点搜索使用文字或已核对的语音转写；语音识别未接通时，不宣称已经自动理解目标。

互助开启且应用在前台时更新所在区域，既有等待任务仍可继续；用户关闭互助或离开前台后停止刷新。已有客户端没有后台唤醒能力，不能承诺锁屏或退出应用后持续主动提醒。

## 三种位置分别保存

| 信息 | 用途 | 更新方式 |
| --- | --- | --- |
| `recorded_location` | 这段声音录制时，作者在哪里 | 每段录音的不可变快照，定位不可用时为空 |
| `target` | 提问、观察或分享指向哪里 | 用户确认的地点、路段或区域；不一定等于作者位置 |
| `presence` | 现在谁可能知道目标地点的情况 | 个人的短期状态，保存采样时间、精度和过期时间 |

回答的 `target` 从问题继承，录音位置独立保存。不得因为用户提到了某个路口、选择了该地点或复用了旧问题，就刷新其现场状态。语音内容中的“这里”只能关联当次有效的位置上下文。

坐标记录包括经纬度、坐标系、精度（米）、实际定位采样时间、定位来源和服务端接收时间。采样时间不能用 HTTP 上传时间替代。录音快照和已确认目标随草稿冻结，重试沿用相同元数据；确认发送时重新检查邀请和当前参与资格，不修改原快照。

以下仅为拟议字段结构，坐标为占位，不能发送给现有 v1：

```text
recorded_location? = {
  latitude, longitude, coordinate_system,
  accuracy_m, sampled_at, source
}
target = {
  place_id, kind: poi | road_segment | area,
  label, selection: current_location | explicit_selection | confirmed_transcript
}
presence = {
  location?, resolved_place_id?, road_segment_id?, direction?,
  sampled_at, received_at, expires_at
}
```

## 单机分工

```text
Android 定位 + 原声 + 用户确认
                 ↓
Sonar HTTP API
  地点适配层 ── 地图供应商：地点搜索、逆地理编码、坐标转换
       ↓
  广场：声音元数据、地点归一、按区域/方向/时效召回候选
       ↓
  个人 Agent：我的关注、互助意愿、静音、已听与任务状态
       ↓
  有限邀请 / 待听原声 → 人自愿回应
```

地图服务提供地理数据，不获取全部用户清单、不替 Agent 决定是否打扰主人。空间召回与个人决策仍在现有 Sonar 单机服务执行，不新增独立 GIS 微服务。

地点适配层负责 `search_places`、`resolve_location` 与地点归一，首版可接高德 Web 服务的地点搜索及逆地理编码。API Key 留在服务端；Android 原生定位负责取得坐标。如果后续改用供应商定位 SDK，SDK 凭证单独按平台配置。地图供应商返回的 POI ID 映射到内部 `place_id`，不让用户手填 ID。相邻 POI、路口与路段可以映射为不同内部对象，不能把最近的一家店当作“所在道路”。

坐标在距离计算前统一。原始 Android GPS 坐标与地图供应商坐标保留来源，适配层按供应商规定转换一次；不能混用 WGS84、GCJ-02 后直接算米，也不能重复转换。

## 两天可交付范围

先保留 FastAPI、SQLite、原声文件与既有任务状态机。只做一个城市、少量演示地点，新增地点表和短期位置字段；当前两用户版本查询有效问题并计算球面距离；位置更新时解析地点，不在每次 inbox 轮询或每个候选匹配时调用地图 API。扩量后再加包围框和地理缓存。

首轮可以按目标周边几百米召回附近愿意互助的用户，但必须标成“附近”，不能据此宣称在同一匝道或同一车道。精度、定位年龄和匹配半径分别设置；建议从“采样不超过 60 秒、精度不差于 100 米、半径 300 米”开始小范围实测。这些只是起始配置，尚未道路验证。位置过旧、精度不足、未来时间戳异常或来源不可信时，不产生自动现场邀请；用户仍可提问。

路况问答尤其要考虑上下层高架、对向车流与匝道。首版不能可靠匹配道路时，不用单个航向角假装完成道路匹配；现场邀请提示“附近有人问”，允许人判断是否了解。可靠的路段/行驶方向匹配留到有道路数据后再做，不能将“附近有人”变成“在同一路段的人”。景区问题可使用 POI 周边范围，景区入口、停车场与整个景区也需分开定义。

用户规模或道路查询需求增长后，再迁移 PostgreSQL + PostGIS，通过空间索引及 `ST_DWithin` 等做半径和区域查询。当前无需为了两个演示用户替换整个数据库。

ESP32 是否提供定位由负责成员决定。无定位能力时可沿用明确标记的演示位置，或后续通过配对 Android 提供位置；不因共享一套 API 就共享另一用户的位置或身份。本轮不改 ESP32 固件。

## 接口迁移与验收

后续情境声音与 POI 公告的空间规则见[声音匹配需求](voice-matching.md)：手选目标允许主动查询，不证明到达；公共公告需明确整个 POI、入口或楼层的适用范围。当前二维附近匹配不具备室内楼层识别能力，不能据此生成“已进入 B2”的触发。自己的问答回复按关系交付，不因离开原目标地点被过滤。到达去重、离开冷却与公告版本替代属于待实现设计，不是本轮位置接口的既有能力。

实施顺序：服务端可选位置快照及地点接口 → Android 前台定位与目标确认 → 广场空间召回 → 双用户设备联调。先增加兼容字段及迁移，再切换真实位置，避免现有 ESP32 协议失效。真实位置路径必须独立于模拟演示验证，不能用模拟结果证明 GPS 已完成。

验收至少包括：

- A 在远处问指定路口，B 在目标附近得到候选；不能因为 A 提到该路口就将 A 标为现场。
- 提问未指定地点时，确认页显示当前定位解析出的目标；拒绝权限后能手选，且手选不触发现场资格。
- 同名 POI 需要确认；定位过旧、低精度、坐标系不符时不误发现场邀请。
- 对向、桥下与高架只凭邻近距离时不声称同一路况；方向不明在提示中体现。
- B 位置有效但关闭互助或静音时不提示；收到回答不等于播放完成。
- 对方获得地点名称、回答及时间，不获得作者精确坐标；原始位置只供服务端必要匹配使用。

## 依据

- [Android 定位权限](https://developer.android.com/develop/sensors-and-location/location/permissions)：用户可能仅授权粗略位置，需要依据实际授权处理。
- [高德逆地理编码](https://lbs.amap.com/api/webservice/guide/api/georegeo)：将坐标关联道路、路口与附近 POI；不是用户实时状态数据库。
- [高德 Web 服务](https://lbs.amap.com/api/webservice/summary)：地点搜索与坐标转换等地理能力。
- [PostGIS ST_DWithin](https://postgis.net/docs/ST_DWithin.html)：后续空间数据库的距离筛选能力，geography 距离以米计。
