## 为什么要做声呐

一家人到了景区，想知道另一个停车场还能不能进。堵在事故后方，想问前面是否开始放行。接人快迟到了，想知道那个路口此刻能不能过去。

这些具体细节可能在现场的人和场所运营方那里。司机想得到答案，需要找到合适的人或消息，又不方便一直找群、翻消息、盯屏等。

声呐想减少的就是这段寻找和等待：让一个出行中的具体需要，更容易得到有用的回应。

以上是用户给出的演示情境，尚未形成访谈或效果数据。

## 声呐是什么

**声呐是以智能车免提语音为入口，按地点和事件连接人与信息的交互语音网络。**

说出关心的事，自己的个人 Agent 帮你找消息、找在场且愿意回应的人，并把回应接回来。车主可以提问，也能留下一句现场观察。运营方维护地点公告。仍适用的声音可以服务后来的需要。

网络同时承接及时往返和异步接话。双方现在方便，就以短语音问一句、回一句。也可以先留下观察，别人需要时再听，或稍后接到自己问题的回应。当前实现采用异步短语音，连续实时多人对讲属于后续独立范围。

### 对讲、微信、地图群和声呐怎样比较

| 产品 | 典型组织方式 | 典型价值 |
| --- | --- | --- |
| 对讲系统 | 频道、队伍 | 一群人及时交流、协调行动 |
| 微信等 IM | 联系人与群关系 | 持续沟通、交换消息 |
| 高德等地图群组 | 队伍或当次出行场景 | 同行协作、交流路上情况 |
| 声呐的产品目标 | 地点、事件、个人需求 | 找适用消息、问现场、接回回应 |

声呐的优势主张落在完整交互上：用户不用先认识回应者或找到群；问完不必一直盯着等；有效的地点声音还有机会帮助下一位用户。这些优势需要用参与意愿、有效回应、重复使用和操作成本验证。

比较依据为产品重心，功能存在交叉。Zello已有回放、存储和异步追听，微信也有语音与位置等能力，高德已有组队、即时通讯和地图群聊。不能把语音、留存、位置或 AI 单个功能称为声呐独有。

## 怎么实现，过程和原理是什么

一个停车问题贯穿过程：

1. 用户说出“帮我问问西门停车场现在还有位吗”。
2. 自己的 Agent 理解地点、问题和意图。
3. 网络寻找适用公告、已有观察或相关回答；需要现场回应时，把明确请求交给合适车主的 Agent。
4. 对方愿意回应，就说出自己的所见，保留本人原声。
5. 回应接回提问者这次需求，继续追问或结束。

不是每次都需要另一位真人介入，已有适用信息可以直接回应。每位车主的个人 Agent 逻辑可共用业务服务，不要求模型之间自由闲聊或每人单独部署。

AI 分工：LLM 听懂、整理语义并辅助匹配；独立决策任务处理内容分类审核、邀请与收听动作；网络服务负责检索、分发、原声来源和需求跟进。固定业务规则与授权不占主讲版面，但继续作为系统约束。

## 商业上怎么走，怎样变现

先在一个停车场或景区入口建立稳定的信息供给：运营方提供基础公告，小范围车主补充观察和问答。先验证对车主有用，再验证运营方愿意付费和续用。

| 阶段／买方 | 付费价值假设 | 收入方式设想 |
| --- | --- | --- |
| POI 运营方 | 管理公告、服务到访者，减少重复问询 | 试点服务费、订阅 |
| 主机厂／集成方 | 车内语音网络接入与运营 | 集成费、运营服务费 |
| 品牌／服务商 | 连接明确需求与真实可履约服务 | 服务费、成交分成 |
| 出行合作平台 | 明确供需匹配、用户转介 | 撮合费、合作分成 |

用户确认已有 xAtom、灵矽及主机厂底座合作意向。声呐首个场所试点、预装、付费和收入尚待落实。上表均为商业假设；品牌服务、拼车和用车撮合后续逐项验证。
