# 声呐 Sonar｜产品定义

> 听见同路的声音。

**声呐是一个由人发声、个人 Agent 辅助参与的城市声音社区。人提问、回答、分享并发布地点信息；广场组织声音；Agent 让主人听到与自己有关系、与此刻情境相关或适用于所在地点的声音。**

更新：2026-10-24。完整产品设计包含下述三类声音，本轮已增加服务端与 Android 前台的情境声音、运营频道及多轮定向交流，本地验证与实机边界见[实现与验收](../development/voice-matching.md)。详细规则与目标验收见[声音匹配与交付需求](voice-matching.md)。

## 2026-10-24 自然交流约束更新

用户要求减少系统介入：在本次已授权现场交流会话中，清楚的现场发言可由Agent自动发布，相关回复在允许的空隙自动播放真人原声，正常成功不逐条读回、询问确认或询问收听。用户选审阅模式才逐条核对。权限、来源、真实问答关系、时效及本地停止仍校验；不把车内闲聊和模型生成内容公开。该会话授权与自动执行机制待实现，后文“每条确认”属于既有实现基线。两端行为见[最新车用交互规范](ux-designs/ux-sonar-2026-10-24/EXPERIENCE.md)。

## 三方分工

| 角色 | 职责 |
| --- | --- |
| 人 | 主动提问、分享观察、自愿回答；经授权的运营人员发布所管理地点的信息，确认发布范围 |
| 广场 | 存储真人原声与转写，组织地点、时间、主题、来源、频道与问答关系，提供有权限且有效的候选 |
| 个人 Agent | 根据主人的行程、关注与交流意愿筛选候选，安排提示和播放，追踪尚未结束的问题 |

广场按权限、关系、地点、方向和时效筛选；个人 Agent 按“我在等谁、我关心什么、愿不愿意帮忙、现在能不能打扰”决定下一步。基础运营告知对适用范围内的可服务用户可见，不因兴趣不同而隐藏；是否出声仍尊重静音与收听设置。公共元信息可以补全结构，不能补造现场事实。

每个人的配置与任务独立保存，程序和服务器可以共用。个人 Agent 的价值是替主人管理注意力、等待回复，而问答的内容与参与决定来自人。

## 三类声音匹配

1. **上下文问答关联**：A 问“现在中环路金科路口堵不堵？”附近且愿意互助的 B 自愿回答，原声明确回到 A 的问题；后续可围绕同一上下文追问。回复对象与可见范围分别明确，离开地点不应丢失自己等待的有效回复。“类似对讲机”描述交流体验，当前采用异步原声，不承诺实时通话。
2. **情境匹配**：A 到达观景点，听见别人此前在此留下的感慨、体验或解说。地点、适用时间与个人兴趣共同影响推荐；历史声音注明日期，不被说成当前现场事实。用户可以主动问“听听这里的故事”，也可关闭自动情境收听。
3. **POI 公共频道**：停车场、景区或商场的授权运营人员发布当前告知，例如“B2 已满，请前往 B3”；进入适用范围的人均可获得有效公告，是否立即出声依个人设置。长期知识按需查询，动态公告必须过期、撤回或被新版替代；普通用户观察不冒充运营通知。

同路通勤、同一目的地是上述匹配发生的生活情境。等待回复、订阅地点或主题是持续关注方式。三类可以叠加：运营公告能引发定向追问，景区解说也能属于运营频道。

人可以拒绝、暂不回应或保持安静。私人助手对话默认不公开；发到广场的声音经本人确认。现场答案保留真人原声、时间与来源；无人回复就说明当前状态。

## 两天原型

只验证一个目标路口、两位用户的“提问→个人筛选→主动提示→真人回答→原声回传”，再用静音或关闭互助展示个人意愿确实生效。Android 已有前台真实定位与 POI 的实现路径，实体设备待验收；旧模拟地点与方向仍须显式标记，附近不等同于同路段或同车道。

ESP32 与 Android 为语音终端；Linx 提供语音交互与工具调用；单台 Sonar 服务器保存广场、每人的配置与任务。新问题事件触发个人规则，在线客户端轮询并播放固定询问提示；不需要为每个人运行独立的常驻推理进程。

情境声音、POI 公共频道与多轮定向交流本轮已扩展实现；两天原型的设备验收与后续 POI 试点仍分别进行。互助、情境收听和频道收听分别表达意愿；共享个人静音约束，不共用业务开关或任务状态。
