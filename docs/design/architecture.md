# 声呐 Sonar｜两天黑客松架构

日期：2026-10-23  
状态：架构设计；服务端已有本地运行实现，平台接入、双端设备和公网部署仍待验收，见[服务端交接](../../server/HANDOFF.md)。

## 1. 产品分工

**人发起问题、提供回答；广场组织声音；个人 Agent 辅助收听与任务追踪。**

| 角色 | 职责 | 决定什么 |
| --- | --- | --- |
| 人 | 提问、分享现场观察、自愿回答、确认公开、设置意愿 | 问什么、说什么、是否参与 |
| 广场 | 存储原声与转写，补全元信息，执行准入与候选筛选 | 哪些消息有效、可访问、与地点或任务相关 |
| 个人 Agent | 理解个人目标，筛选候选，安排提示与播放，追踪问题和回复 | 是否值得打扰主人、何时播放、还在等什么 |

广场按权限、地点、方向、时效和问答关系提供候选；个人 Agent 根据本人的关注、参与意愿、静音状态和已听记录决定处理方式。共用筛选函数与部署服务，个人状态仍按用户隔离。

这里的 Agent 辅助驾驶期间的语音交流与注意力管理。它不自动替人提出公共问题、编造现场答案或执行车辆控制。人创建任务后可以让 Agent 持续跟踪，直到收到回答、取消或过期。

## 2. 两天范围

确定约束：ESP32 客户端、Android 客户端、单台自有业务服务器；ESP32 硬件与固件由对应成员实现，本方案只定义接入边界。

采用 Linx 云端语音交互。自有业务服务器部署 FastAPI、SQLite 与本地音频目录。“单台服务器”指自有部署范围，系统依赖联网访问 Linx。

**主场景只做一个：中环路金科路口的现场询问与原声回答。** 路口、方向与位置为明确标注的模拟配置。

| 必须完成 | 延后 |
| --- | --- |
| 人发起现场问题，人自愿回答 | 自动生成问题、代替人回答 |
| 个人策略主动提示一个相关请求 | 全城广播、后台无限自主推理 |
| 原声收发、问答关联与任务状态 | 开放语音房、实时多人通话 |
| 自己决定互助、静音、退出 | 复杂兴趣学习、长期记忆 |
| 一个固定现场与预设方向 | GPS、道路拓扑、导航接入 |
| 两端完成主流程 | 跨设备账号同步、独立运营后台 |

同路通勤闲聊与同目的地交流属于产品场景，待主闭环通过后再用同一消息机制补充展示，不作为额外两套必交付流程。

## 3. 现场互助主流程

1. A 进入“问附近的人”入口，选择目标路口，录制：“现在中环路金科路口堵不堵？”确认公开。
2. 广场保存原声、转写、提问者、目标路口、方向、时间与问题ID，建立待回复任务。
3. 新问题进入该地点的候选消息流。B 的个人策略检查：自己当前处在该现场、本人开启现场互助、位置配置有效、未静音、未被同一问题提醒过。
4. B 客户端获得邀请。在音频空闲时播放短提示：“有人询问中环路金科路口堵不堵，愿意回应吗？”随后响一声“滴”。
5. B 自愿开始回复：“好堵啊，下匝道都要十五分钟。”回复录音绑定当前问题ID，确认后公开。原型可用按键开始回复，不做持续后台录音。
6. 广场将回复关联到问题，更新任务。A 的 Agent 在允许收听时提示并播放原声；静音时保留待听状态。
7. A 可结束任务。若无人答复，则显示或提示“暂时无人回应”；请求过期后不继续打扰 B。

A 的提问目标不是 A 的当前位置。B 的当前地点也不能由“提问里提到了这个路口”推断。

“十五分钟”作为回答者的个人陈述保存；播报注明时间与来源，不自动变成全路段通行时间预测。示例路况属于演示内容，不是已核实的真实路况。

## 4. 系统结构

```text
       人 A / Android                 人 B / ESP32
          │      │                       │      │
          │      └───── 语音 WSS ─────────┘      │
          │                   │                 │
          │              Linx 云平台            │
          │           每人独立语音会话           │
          │                   │ MCP             │
          ↓                   ↓                 ↓
  ┌────────────────── 单台 Sonar 服务器 ─────────────────┐
  │ 客户端 HTTP API           Linx MCP 工具               │
  │                                                      │
  │ 声音广场：原声 / 转写 / 元信息 / 候选 / 问答关系       │
  │          ↓ 新问题或新回复事件                         │
  │ 个人任务：独立配置 / 策略 / 邀请 / 待听 / 超时         │
  │                                                      │
  │ SQLite                  本地音频目录                  │
  └──────────────────────────────────────────────────────┘
```

个人 Agent 在实现上由两部分协作：Linx 处理用户语音与工具调用；Sonar 服务器按用户执行任务和提示规则。后台提醒不要求 Linx 自行唤醒或为每条消息启动一次 LLM 推理。

两端通过 HTTPS 上传公开录音、确认、取通知和下载原声；通过 Linx WSS 与自己的助手对话。固定请求提示采用预录系统素材，正文原声通过 Sonar 传输。系统提示不伪装成现场真人声音。

## 5. 广场元信息与候选筛选

| 信息 | 来源与处理 |
| --- | --- |
| 原声、作者 | 客户端上传音频；服务端由设备凭证确定作者 |
| 转写 | Linx STT 与本轮录音配对；不确定则重录或保留草稿 |
| 内容类型 | 原型由“现场提问 / 回答 / 分享”入口给出，不增加独立分类模型 |
| 目标地点与方向 | 从预设列表确认，不靠模型自行生成任意地点ID |
| 当前所在地点 | 来自该用户独立的模拟现场配置，标记 source=simulated 与更新时间 |
| 创建与发布时间 | 服务端记录；内容时效与位置时效分别检查 |
| 问题与回复关系 | 客户端从当前邀请取得 question_id，服务端校验 |
| 信息属性 | 个人观察、转述或未知；默认不赋予事实认证 |

元信息补全增加结构，不能补出原话没有表达的事实。重复转述不能算多份独立证据。

候选召回使用 SQL 过滤有效消息。对于现场回答邀请，按每个人的现场上下文查询 place_id 与适用方向的有效问题，再执行本人的参与策略。两人原型中，除提问者外只有一位可能回应的人；不实现全局回答者排名或多人抢答。广场提供相关声音，是否提醒由各个人策略决定。

## 6. 个人策略与任务

### 个人配置

```json
{
  "user_id": "bob",
  "linx_agent_id": "预先创建的独立AgentID",
  "device_id": "预先绑定的设备ID",
  "presence": {
    "place_id": "zhonghuan_jinke",
    "direction": "demo_exit",
    "source": "simulated",
    "updated_at": "由服务端记录"
  },
  "assist_enabled": true,
  "mode": "listen",
  "focus": "愿意回答附近路口的拥堵问题",
  "revision": 1
}
```

原型的后台策略是可解释规则：本人同意互助、当前地点和方向符合、位置未失效、问题有效、未静音且未重复提醒。实际运行分别读每个人的配置，不由一个全局模型统一决定所有人的偏好。Linx 可通过 set_focus 更新有明确含义的参与设置；不能只保存一句自然语言而不改变实际开关。

### 请求级任务

```text
问题：待确认 → 等待回答 → 已有回答
                        └→ 已取消 / 已过期

回答邀请：待提示 → 已提示 → 已回复
                         └→ 已拒绝 / 已取消 / 已过期

原声交付：待听 → 已播放 / 已跳过 / 已取消
```

等待回答与待听是不同状态：A 已收到回复但处于静音时，问题可以有答案，音频仍未播放。

每个任务关联 question_id、recipient_user_id、request_id、expires_at；个人筛选和播放另记录 profile_revision。问题取消或过期、B 拒绝、参与模式改变时，相关待提示任务立即失效。已排队和迟到的工具结果在取出及播放前再次校验。

一期不自动转问更多人。邀请被拒或过期后向 A 返回实际状态，由 A 决定是否再问。位置 TTL、问题 TTL、提醒间隔作为演示配置显式设置；不能把演示时间窗口当作真实驾驶环境的验证结论。

## 7. 接入与接口边界

### Linx 接入

已查阅文档，未做账户或设备实测：

- [设备协议](https://linx.qiniu.com/docs/xrobot/platform/websocket)说明语音帧、STT/TTS 与手动录音控制。
- [云端 MCP](https://linx.qiniu.com/docs/xrobot/mcp/software-mcp)说明工具调用及设备、Agent、会话身份 Header。
- [OTA 网关](https://linx.qiniu.com/docs/xrobot/platform/OTA)提供激活与连接配置；Android 设备注册流程需实测。

预先创建演示用户与 Agent、绑定设备。平台管理 API Key 留在服务器。MCP 使用可验证的专用凭证，校验后再读取身份 Header；不能仅凭可伪造 Header 授权。凭证如何在平台配置和透传属于首批验证项。

### 三个 MCP 工具

| 工具 | 用途 |
| --- | --- |
| `get_feed` | 返回本人的关注、任务状态、至多十条合法候选及来源；使用 request_id 标记本轮 |
| `set_focus` | 修改本人 focus、assist_enabled、mode 等允许字段并递增 revision |
| `queue_voice` | 从本轮合法候选选择原声；校验用户、request_id、revision、时效并去重 |

主动的现场邀请由业务事件触发，无需新增“自主 Agent”框架。公开提问使用客户端入口和确认流程，不通过模型自动发布。

### 客户端 HTTP API

| 接口 | 用途 |
| --- | --- |
| `GET /v1/me` | 本人配置与绑定信息 |
| `PUT /v1/me/context` | 更新模拟现场、关注与收听意愿 |
| `POST /v1/posts/drafts` | 上传原声、转写、client_request_id、kind、target_place_id 或 reply_to |
| `POST /v1/posts/{id}/confirm` | 确认草稿；发布问题或绑定到有效邀请的回复 |
| `POST /v1/questions/{id}/cancel` | 提问者结束任务并撤销待处理邀请 |
| `GET /v1/questions/{id}` | 提问者查询等待、回答、取消与过期状态 |
| `GET /v1/inbox` | 返回本人的有效邀请、任务状态或待听原声 |
| `GET /v1/inbox/{id}` | 实际出声前复核当前权限、版本、时效与可播放状态 |
| `POST /v1/inbox/{id}/ack` | 回执：已提示、已播放、拒绝、跳过或失败 |
| `GET /v1/audio/{id}` | 检查权限及内容状态后返回原声 |

原型每个用户一个主终端。客户端 Token 映射用户，模型与客户端均不能传 user_id 来取得其他人的权限。开发时的请求字段、响应、状态和幂等约定以[三端接口契约](../development/contracts.md)为准。

### 音频与轮次

Sonar 文件协议：WAV、16 kHz、16-bit signed little-endian、单声道，每条上限八秒。音频以二进制上传；Linx WSS 输入输出格式按实际握手参数处理，两者不混用。

每端一次仅处理一条录音。保存本地录音轮次、当前邀请及对应 STT；确认绑定具体音频与转写版本。STT 示例没有业务轮次与最终片段保证，必须实测结束和超时条件；识别片段归属不明时不公开。

公开稿在确认前仅作者可见。转写基础检查与预先人工核验样本用于封闭演示，不能据此宣称完成全面原声音频审核。真正公开后才供其他人筛选与收听。

## 8. 主动提示与播放

客户端在当前演示会话存活时，约一秒一次轮询 inbox。服务器发布问题后执行候选及个人策略，生成持久化邀请；因此 B 不需要自己先说“听听新消息”。不实现系统级离线通知或应用被关闭后的唤醒。

邀请使用固定提示音和一个路口的预录系统提示。Android 同时显示询问原文；用户可主动听原问。这个实现不依赖动态 TTS 推送或 Linx notify 具备任意业务通知能力。

客户端串行协调录音、Linx TTS、系统提示和真人原声。正在说话或录音时延后提示；超过邀请期限则丢弃。TTS 已结束需要确认本地缓冲已排空；没有开始 TTS 或已断连时走明确的取消或空闲处理，不能无限等待 stop。

同一邀请只提示一次。播放成功后再回执；回执失败重试回执，避免立即重播。静音和停止在本地立即生效。静音撤销待提示邀请，回复原声保留待听；停止只结束本次播放，提问任务通过明确的取消操作结束。

配置版本变化使旧播放指令失效，恢复收听后按当前配置重新生成有效播放请求。服务端验证状态，客户端也在实际出声前检查。应用重连后先恢复状态，不重播已处理任务。

## 9. 单机实现

| 表 | 内容 |
| --- | --- |
| `users` | 用户、设备、Agent 绑定，设备Token哈希 |
| `profiles` | 当前现场及更新时间、参与开关、关注、mode、revision |
| `posts` | 问题或回答、原声、转写、作者、target_place_id、reply_to、发布状态、问题状态与期限 |
| `deliveries` | 用户、question_id、request_id、类型、配置版本、处理状态、截止时间与回执 |

邀请与待播原声复用 deliveries。邀请以“用户 + 问题 + 交付类型”唯一约束去重，原声以“用户 + 原声帖子 + 交付类型”唯一约束去重；发布草稿以“用户 + client_request_id”去重。问题确认、取消、回答与交付生成在短事务内一致处理；网络请求不放在事务内。

服务为一个 FastAPI 进程，挂载业务 API 和 SSE MCP；SQLite 存持久状态，本地目录保存原声与提示素材。HTTPS 代理与应用部署在同一台服务器，数据目录持久挂载。无需 Redis、向量库、任务集群或本地模型服务。

事件处理按少量演示用户直接调用个人策略即可，超时在取任务和周期清理时检查。重启后从持久状态恢复，过期任务不再投递。单机单进程不承诺高可用或全城规模。

Android 中提供一张简单的任务卡：提问、候选现场、本人意愿、邀请结果、回答及时间。处理原因从实际规则与引用记录生成，不展示或伪造模型思维过程，不另建仪表盘项目。

## 10. 开发与验收

第一条开发闭环就是“问题→个人策略→真实设备提示→真人回答”。允许先用标明来源的预置录音测试链路，再接现场录音；不能把个人化推迟到所有基础功能做完以后。

| 顺序 | 可检查结果 |
| --- | --- |
| 首先验证平台 | 两端语音往返、MCP身份与凭证、独立原声播放可用 |
| 第一天闭环 | 预置问题触发 B 的个人策略及设备提示，回答能回到 A；A、B 上下文不串用 |
| 第二天完善 | 现场发问与回答、静音反例、超时与取消、去重、重启和路演 |
| 核心通过后 | 补充同路闲聊与同目的地候选，复用现有接口 |

ESP32 成员负责设备协议、提示、录音与播放；Android 成员负责交互、同协议及任务卡；服务端成员负责广场、个人策略、任务与 Linx MCP。客户端“可与 Linx 聊天”不足以完成验收，还必须验证独立原声传输和任务提示。

完成标准：

1. A 现场发问，B 在无主动查询的情况下收到一次相关提示，真实回答回到 A；连续三轮不串问题。
2. B 在同一地点开启静音或关闭互助后，新问题不出声；恢复参与后新问题重新生效。
3. 超时、取消、拒绝和位置失效不会触发迟到提醒；无回应时 A 得到真实状态。
4. 未确认草稿不公开，别人的任务与私人录音无法越权访问；重复上传或确认不重复发布。
5. 单机运行并可重启恢复；Linx 或网络故障有明确反馈，不能宣称任务仍在线执行。
6. 静止环境完成体验验收；位置为模拟，不宣称完成 GPS、驾驶负荷或真实车机验证。

架构评审见[评审报告](architecture-review.md)。

具体排期与三端 AI 任务包见[两天开发入口](../../two-day-development.md)。
